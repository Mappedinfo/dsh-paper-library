# Documentation site on GitHub Pages

Every page of <https://mappedinfo.github.io/dsh-paper-library/docs/> is rendered from markdown
that is already public in this repository. The landing page draws its books from the same list,
so a book only exists when a document backs it, and the sentence the reader sees when the cover
is pulled out is that document's own first paragraph.

## What the reader is shown

`docs-site/landing.html`, `docs-site/landing.css` and `docs-site/landing.js` are copied to
`_site/docs/_assets/` and produce one scroll-driven scene in three beats.

| Beat | What happens | Where it is decided |
| --- | --- | --- |
| Open on a sea of books | dozens of CSS-3D volumes at seeded distances, thicknesses and angles, with page edges, ribbons and tabs on the near ones; the site name, one line and 「查看文档」/「GitHub」 sit in a clear centre | `layout()` reseeds its scatter to 20261112 and `pickClear()` keeps the centre free, so the wall is the same on every visit |
| Scroll, and the books shelve | the same volumes turn upright and travel onto ten shelves ordered by documentation topic; 「直接进入书架」 puts them there without the walk, and normal scrolling still works afterwards | `pose()` interpolates each book between its sea slot and its `packRows()` shelf cell across a 340vh `.drive` section |
| Open a book | the cover lifts into a reading panel: one highlighted sentence from the paragraph, a margin note, a sticky note tucked between pages, and links into the real document's sections | `openReader()` |

Hover pulls a book out with its title and preview; clicking it opens the panel; the document page
behind the panel carries a table of contents, in-page anchors, a left rail to every other
document and a search box. Search is static — `scripts/build-docs-site.mjs` writes
`_site/docs/_assets/search.json` from the same render pass, and the browser matches every term
against titles, section headings and body text and marks the hits. Nothing is fetched at run
time except files inside `_site`.

Phones drop the hover dependency and the long drift, keep the whole shelf without side-scroll,
and the reading panel stays a single legible column; `prefers-reduced-motion` skips the walk and
shows the shelf directly.

## Where the content comes from

The build collects `README.md`, `README.en.md` and every `.md` under `docs/`, and each file is
assigned to a shelf in the `SHELF_OF` map at the top of `scripts/build-docs-site.mjs`. **A
published markdown file with no shelf fails the build** rather than silently vanishing from the
wall, which is the same reason the page count and the book count are asserted equal in the
static check below. Links are rewritten so a reader on Pages follows a Pages URL — including the
`#anchor` forms the plugin's own documents use — and remote badge images are drawn as text chips
instead of asking someone else's server to render a page.

Two receipts, both regenerated by a command and both committed:

| Command | Proves | Receipt |
| --- | --- | --- |
| `npm run verify:docs-site` | the generated tree against the markdown it came from: coverage, one title per page, books that name real documents, quoted sentences that exist in the sources, no outside asset, no machine-local path, the demo labelling, the workflow wiring (7 checks) | [docs-site-static.json](validation/docs-site-static.json) |
| `npm run test:docs-site` | the same site in real Chromium: the first frame is a sea of books with an uncovered centre, shelving is one continuous path, every book rests inside its topic shelf, hover previews a real paragraph, the opened book quotes one verbatim, search marks hits, a search result jumps to that section, the direct-shelf entry works, phone and reduced-motion paths hold, and every published page loads without page errors or third-party requests (18 checks) | [docs-site-browser.json](validation/docs-site-browser.json) |

```sh
npm run build:docs                      # _site/docs/ only
npm run verify:docs-site                # offline gate, no browser
PLAYWRIGHT_MODULE=/path/to/playwright/index.mjs npm run test:docs-site
```

Playwright is not a package dependency here — the fixture imports it through
`PLAYWRIGHT_MODULE`, like the other browser fixtures in this repository — and `test:docs-site`
serves the built tree on `127.0.0.1` itself, so no deployment is needed to run it. It writes the
screenshots a person can look at into `artifacts/docs-site/` (ignored by Git) — one per beat on
desktop (floating, shelving, shelved, hover, opened book, document page, search, reduced motion)
and four on a phone viewport.

## Publishing

`.github/workflows/pages.yml` runs `node scripts/build-site.mjs`, which assembles the
whiteboard at the Pages root and calls `buildDocsSite()` to write the documentation beside it
under `/docs/`, then uploads `_site` with `actions/upload-pages-artifact` and deploys with
`actions/deploy-pages`. Its trigger paths cover `docs/**`, `docs-site/**`, either README and the
two build scripts (alongside the whiteboard's own inputs), and the workflow also runs on
`workflow_dispatch`. Pages needs enabling once in the repository settings (Source: GitHub
Actions); after that the workflow self-deploys. Every asset path is relative, so the `/docs/`
subpath needs no base configuration.

## What the site does not do

It is a static read of public documents: no model call, no server, no plugin runtime, no
managed library, no PDF and no private catalogue path. The highlights, margin notes and sticky
notes inside the scene are this site's own typography, said so by the flag under the wall —
「场景中的高亮、页边批注与便签属于本站的演示排版」 — and they make no claim about annotation
export or handwriting recognition, which the documents describe themselves.

Both receipts describe the build checked on this machine, and the browser fixture serves that
build rather than the deployed URL. After a publish, confirm the live site by loading
`/docs/` and re-running `node scripts/verify-pages.mjs` for the whiteboard at the root; the docs
site does not yet have its own live-URL check.
