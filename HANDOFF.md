**Current renderer optimisation against Excalidraw (2026-09-21):** the drawing path was compared line by line with Excalidraw's renderer — `renderer/staticScene.ts`, `interactiveScene.ts`, `renderer/helpers.ts`, `components/canvases/StaticCanvas.tsx`, `element/src/renderElement.ts` and `collision.ts`, read from a source download rather than a summary — and the full comparison table lives in [docs/whiteboard-design.md](docs/whiteboard-design.md). Two findings were worth acting on and the rest were recorded as deliberate non-adoptions.

The first was a genuine leak: dragging a line out of a node's connect handle appended a fresh dashed preview path on every `pointermove` and never removed the previous one, so a 40-step drag left 40 identical paths in the edge layer for the browser to repaint (measured: 11 paths mid-drag → 1 after the fix). The gesture now owns a single preview element whose `d` is rewritten, withdraws it when the pointer is over no node, and one `cancelDrag()` teardown removes it on release, on a mid-gesture error, when the view closes and on dispose.

The second was the persistent-scene property Excalidraw relies on: `render()` discarded and rebuilt the whole node/edge tree, which cost ~1,200 element creations and ~3,700 `setAttribute` writes at 150 nodes for every selection, rename or save-status change. It now reconciles keyed by board id — create what is new, update in place, remove what left — and the attribute writes are conditional, because writing the same string still invalidates the element. Measured on a 150-node/149-edge board in Chromium: **1,197 → 0** elements created, **3,743 → 151** `setAttribute` calls, `render()` 1.9 ms → 1.4 ms. The JS time was never the problem; the mutations were.

The same measurement applied to a drag found the pattern once more: `redrawGeometry` — the cheap path — rewrote every node and every edge on every pointer move. It now takes the ids the gesture touched (a move passes the dragged set, a resize its one node, a bend-point drag the two endpoints, and the connect gesture, which moves nothing on the board, no longer calls it at all). The canvas supports pan/zoom, text/note/rect/ellipse/diamond nodes, drag and resize, connecting by dragging a handle, marquee multi-select, undo/redo, copy and delete, keyboard nudging and a real Fullscreen API. Papers drag from the visible library shelf onto the canvas as nodes bound to `paper.id` (title/year/citekey copied at drop time; a missing year is omitted, never guessed) and double-click back into the reader; a keyboard-reachable picker adds one or many, and "用勾选的文献新建画板" builds a new arranged mind map (theme root plus one node per paper). A selected knowledge-graph node joins the current board through the graph panel's own control (`onAddToBoard`), because the graph and the board occupy the same column and cannot both be visible; a paper-typed graph node keeps its paper binding and anything else becomes a concept node carrying only the label the graph showed. "整理成树" applies a deterministic tidy-tree layout (parent centred between first and last child, per-depth columns sized by the widest node, idempotent on a second arrange) and leaves unconnected nodes as further roots below.

The board is a reference source for the conversation: "放入对话" freezes a content-addressed snapshot (`board-ref:<sha256>`, immutable — editing or deleting the board never rewrites it), inserts a `[[paper-library-board:v1:<boardId>:<hash>]]` chip through the plugin's own `@` source (`paper-library-boards`, order 30, alongside annotations), and the host expands it at `agent/pre-step` into a `〔引用画板 …〕` marker plus a separate user message sourced `paperLibraryBoard` with a `body_hash`. At most four groups share the annotation character budget (24,000 default); a malformed, missing or identity-mismatched reference fails the turn instead of sending anything else. Board snapshots are deliberately not session-bound, because a board is cross-paper. The agent can work with boards through the 30th tool, `library_board` (`list|get|create|save|delete`); model additions and edits are marked `origin:'llm'` by diffing against the stored board, untouched content keeps the reader's authorship, a model-authored board stays `needs-review` until the reader saves it, and only the reader can call `board_accept`. Provenance is decided by the caller, never by the payload: a browser request is always a reader write, and a browser cannot request a model write or reach the `board:` namespace through the state API.

Four decisions were revised while building, each from an observed failure: the board occupies the workspace's second column (a fixed overlay hid the shelf and made drag-in impossible); accepting AI proposals is explicit (`board_accept`) because automatic saving would otherwise launder proposals into reader content; closing the board, switching boards or unloading the page settles the debounced write (a fixture reload inside the debounce window lost a node, and a pending save could also resurrect a deleted board); and a failed listing reports itself and creates nothing instead of fabricating an empty board. ## Accepted goal and current result

Independent low-memory literature plugin in Mappedinfo, integrated with DeepSeek Harness. Provides quick import/search, APA 7 clipboard, individual/full-library BibLaTeX export, continuous PDF reading, native persistent annotations, a typed evidence graph and one native Harness conversation per paper. Zotero is optional input, not a runtime dependency or canonical store for this plugin.

The accepted reading workflow uses one reference collection per question in the same native conversation in the plugin and Harness main page. New/updated, manually selected and all-user-note shortcuts add to that collection; later saved notes prompt explicit addition. Search, page filters and pagination preserve selection. Temporary selected PDF text can coexist with saved notes. Opening a paper creates or reuses a durable cold Session without starting an Agent or model call. Initial model selection follows the source conversation's public projection or Harness default; later choices belong to the paper Session. Automatic sending remains opt-in and off by default. Complete AI replies can be saved individually to PDF with native Session/message provenance.

Current source checks exact selected PDF versions and full source text before writing a private immutable snapshot. Metadata selection holds at most 1,000 notes with 240-character text/comment previews; source preparation defaults to 24,000 Unicode characters, configurable from 1,000 to 96,000, and rejects overflow rather than truncating. A frozen canonical token works through either native input or the plugin. The public Host pre-step extension logs exact source content using a generic `Paper Library` plugin context, with identity/version/hash metadata outside model text. Only that verified, durably flushed log evidence updates the native usage projection; queue acceptance or a plain user token alone does not. The projection retains at most 5,000 last-sent annotation versions and reports eviction.

LaTeX projects are implemented as a verified backend: a folder holding sources and its PDF is registered in `latex_projects` (plus `latex_revisions` history), read and written through `library_latex` / `library_latex_edit` (16 bridge-whitelisted actions), compiled with the user's own `latexmk` in that folder, and rendered through the existing PDF pipeline. Writes are atomic, revision-checked and confined to the project root; compiling reports exit code, `-file-line-error` lines and a log tail instead of masking failures. Measured: a one-page Chinese article builds in ~0.3 s. The workspace keeps its own manuscript folder under the DSH home (default `<DSH home>/manuscripts`, `latexRoot`/`DSH_PAPER_LIBRARY_LATEX_ROOT` override) and adds it as one `paper-library-latex` source to the sync service's config on first use (timestamped backup, idempotent, additive only; the sync plugin's own template now lists it too). Projects are created from the ☰ menu into that folder with an optional starter `main.tex`; registering an arbitrary existing folder stays available in the same menu. Layout is source-left/PDF-right with a draggable divider persisted as `latex_split`; DSH questions and co-writing are registered into the library's shared reading rail (`registerPanel`/`setExternal`, the same rail as 批注, with its side preference and saved width) and fall back to a workspace tab when no rail is present; the rail closes cleanly with no leftover empty column. Idle recompiling (2.5 s, serial, existing-PDF projects only) is on by default. The editor/preview panel is implemented (`web/latex-workspace.js`): project and file selection, a line-numbered editor with 900 ms autosave and a serialized save queue, a compile button that lists `-file-line-error` lines, PDF page preview through `latex_pdf_page`, a conflict banner that offers "load newest / overwrite with mine" instead of overwriting, per-file diff and two-project comparison, and in-panel registration of a new folder with its starter. It is verified by `docs/validation/latex-workspace-browser.json` (13 checks, real Chromium against a real worker and a real latexmk build, zero external requests). DSH questions and human-machine co-writing are implemented in `src/harness/latex-ai.mjs`: `latex_ai_ask` answers inline from a bounded excerpt or selection without touching the file, and `latex_ai_propose` turns the model's exact-string replacements into a reviewable proposal (anchors must occur exactly once; only replacements are stored), which `latex_ai_accept` applies through the same revision-checked `latex_write` labelled `ai:<provider>/<model>` and refuses with `STATE_CONFLICT` when the file moved on. The panel exposes both under the editor, and the browser receipt covers the review/accept/discard flow. Remaining: a Markdown → LaTeX import path (rules from MarkTex, offline, no browser WASM); optional panel polish (syntax highlighting, partial acceptance). See [docs/latex-projects.md](docs/latex-projects.md).

The data-sync adaptation is implemented and optional: `externalSources` / `syncConfig` (deployment config) and the live settings `sync_config` / `external_sources` index PDF folders another sync service already maintains. A sync config only *offers* `kind: directory` roots (never anything inside `$DSH_HOME`, which holds state); indexing requires a selection (`{"select":"all"}` or `{"id":"sync-…"}`), and one root keeps one source id — a second id for an already indexed root is refused with `conflict` instead of duplicating its records. Indexing creates one symlink per PDF under `<library>/external/<source>/…` (a single access address) plus a catalog row whose metadata comes only from the filename (`parse.field_sources = synced-filename`, `needs_review`, tag 外部同步); PDFs are never opened and never hashed during a scan, unchanged files are skipped from durable size/mtime records, and at most 200 new files (limit 2,000) are indexed per call with `pending` reporting the remainder. Measured in `docs/validation/external-scan.json`: 2,000 synthetic PDFs index in about 0.7 s and rescan in about 0.05 s. Rename detection is keyed on the containing directory plus size (`external_files.parent`, indexed), with the older size-only rows migrated in place on first open. `pdf_path` serves the staged link, and every write promotes the file into `pdfs/` first, so a synced directory stays byte-identical. Disappearing files are flagged, not deleted. The Vault Sync side proves with `tests/symlinks.test.mjs` that its scan ignores symbolic links, so nothing is uploaded twice. Design: [docs/external-sources.md](docs/external-sources.md).

The added intake requirement is implemented: drop/select multiple PDFs or paste links/DOIs to fetch, parse, name and save managed copies; embed an independent DSH adaptation of `paper-fetch-skill` named `paper-library-fetch`. The skill uses the calling session and plugin tools. Exact parsed-title evidence gates online bibliography enrichment; metadata-only acquisition and incomplete parsing remain explicit. No external browser/MCP fetch runtime is installed.

User capacity target is approximately 2,000 records and 1,000 PDFs. Source Zotero data and existing PDFs were not migrated or modified during implementation.

## Known limits and next validation

Language output and suggested vocabulary need reader judgment. Generation sends the explicitly selected text to the paper's configured DSH model and consumes that model's quota; local persistence does not mean local model inference. Standalone preview can review records but generation requires DSH. Records are bounded at 256 KiB; saves below 60,000 UTF-8 request bytes use keepalive, while larger pending saves require the page to stay connected. Abrupt host/browser termination before acknowledgment cannot guarantee saving unsent text. Malformed or oversized legacy browser drafts remain in place with a migration error rather than being silently deleted.

**Accepted reference update (2026-09-14, implemented):** [Continuous annotation references](docs/annotation-reference-design.md) now documents current behavior. The accepted implementation adds additive selection, exact source budgets, frozen snapshots, logged usage and official input references. Do not revive the old replace-only selection or silent 40-note/1,500-character truncation in native chat.

**Accepted implementation complete:** automated, native integration, browser, scoped memory and existing-profile installation checks all pass. Follow the boundaries below for additional validation; they are not claims of real-library, WPS or provider-quality coverage.

1. **WPS viewing/saving:** native application automation failed to complete opening the synthetic copy. Validate standard highlights/comments and embedded metadata after WPS save on a copied file; do not claim WPS compatibility from PyMuPDF-only tests. Existing user documents were not edited.
